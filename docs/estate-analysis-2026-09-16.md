# Incubator Agent OS — estate analysis (2026-09-16)

Inputs: BAI Metrics Data Collection Template v5; Notetaker; ImpactOS (impactos, impactos_db_health); Coach OS (impactos-coach); Founder OS (impactos-founder); Coaching Agent; BAI Metrics / baimetrics / BAI_Partner_Site / lsns_impactos.

## The BAI template (v5)

Five sheets plus an industries reference:

| Sheet | Grain | Key fields |
|---|---|---|
| Companies | one per company | name, former name, business number, founder, address/city/province, phone/email/web, industry, underrepresented group flag + 9 group booleans + prefer-not-to-disclose, company type (Startup/SME/Industry Partner/Ecosystem Partner/Academia/Government) |
| Company Updates | one per dated snapshot | support programs attended, total VC/angel/debt/grants (cumulative CAD), lifetime revenue, revenue disclosure (Disclosed/Not Disclosed/Pre-revenue), program, stage of growth, current FTEs, cost of support (CAD), notes |
| Contacts | one per person | name, title, email, phone, primary flag |
| Programs | one per program | name, description, type (Accelerator/Cohort/Workshop/Event/Mentorship), dates, status (Active/Completed/Planned) |
| Program Cohorts | one per company-in-cohort | program, company, cohort name, dates, company status (Active/Graduated/Withdrawn) |

Canonical stages (v3): Idea, MVP, Early Adopters, Growth, Scale. Partner terms normalised centrally (`STAGE_MAPPING` in baimetrics).

## Gaps (net-new)

- Conversational interview agent — nothing in the estate does this.
- Demographics: ImpactOS holds them on `people` (`diversity_and_inclusion` enum[] — 2SLGBTQI+, BIPOC, Female, Person with a disability, OLM, Youth, Newcomers, Canadian veteran; `racialized_groups` enum[] with 11 values, enum name has trailing-space typo). BAI collects per company with 9 booleans + prefer-not-to-disclose. LSNS populator collapses person→company via substring matching (`lsns_impactos_to_template.py:parse_underrep_groups`). Vocabularies differ (BIPOC vs Indigenous/Black/Racialized; veteran vs PND). Starter schema: record per person, derive company flags in a view, versioned vocabulary + mapping like stages.
- Funding: Founder OS HAS a funding-events table — `company_funding` (`impactos-founder/supabase/migrations/20260505_create_company_funding.sql`): one row per event, type ∈ {angel, venture_capital, grant, debt}, source_name, amount, close_date, round_name, grant_program_name, is_active. Maps 1:1 to BAI's four cumulative totals (sum to date). RLS: founders + admin/editor only; coaches/advisors blocked — a policy choice the starter must revisit since reporting needs totals. BAI uses cumulative totals per update; legacy ImpactOS uses period deltas in JSONB. Issue #236 (high-water-mark) unresolved.
- Team: Founder OS has `company_employees` (roster: name, email, is_founder, is_active, has_product_skill, has_sales_skill, user_id) + `company_team_monthlies` (company × person × month: hours_per_week + same flags; `company_team_latest` view). FTEs derivable (Σ hours/40 or active headcount); BAI's single "Current FTEs" is a lossy roll-up.
- Monthly metrics: `company_monthly_snapshots` (typed, cents CAD): arr, paying_customers, cac, arpu, avg_lifetime_months, cash_on_hand, monthly_burn, runway_months, biggest_challenges, biggest_wins; one per company per month keyed to `company_submissions`. Cleaner than BAI sheet or ImpactOS JSON. Missing vs BAI: stage of growth, lifetime revenue + disclosure, cost of support, program membership.
- Design implication: Founder OS already solved grain — facts at natural grain, BAI totals as views. Inherit that shape.
- Cost of support: only derivable from `support_time_entries.hours × advisor_profiles.hourly_rate`; no per-company-per-period roll-up.
- Cross-meeting person identity: Notetaker participants are per-meeting, email-keyed.
- Action items / decisions as structured records: absent everywhere (Markdown headings only).

## What breaks most in practice (BAI ingest)

Populators emitting blanks on renamed source columns; unmapped industry tags dropped silently; companies with no cohort vanishing from time series; reading the wrong source table; dates as text / just outside window; blank-vs-zero ambiguity; partner round-trip latency.

## Decisions (grill, 2026-09-16)

1. **Deployment model: one organisation per database.** Not multi-tenant. No `tenant_id` columns; a single `organization` row for operator identity/config. Cross-org aggregation happens at export via the BAI template contract, not in a shared DB. RLS is role-based (staff / coach / advisor / founder / funder-readonly), user JWT never service key.
2. **Stage vocabulary: track-based milestones from ImpactOS Multi Tenant**, not the BAI five. Tracks: Software, Hardware, Medical Device, Biotech/Pharma. System tracks stored once, forkable. Position stored as dated history; objective (target) kept separate; BAI stage derived via `bai_stage` on each definition. Drop the parallel `commitment_tracks` model.
3. **Founders can add and submit data**, but never write fact tables directly. All founder input lands in a submission inbox (Founder OS pattern: submission → parsed + confidence → llm_runs audit → accepted → typed fact). Same proposer/approver discipline as agent writes (Coach OS preview-then-confirm). Founder role + company membership in migration 001; founder-facing surfaces (hosted form, email reply, founder-run skill) after the staff path. Acceptance policy configurable per field class (auto-accept metrics; review for stage/funding/demographics).
4. **Built for other incubators; Volta keeps Coach OS / Founder OS.** No parity requirement (no applications, agreements, evals, seat selection). Product = schema + ingest discipline + skills. Needs a named first adopter with real artefacts before migrations are "done". Proposed: LSNS (runs retired-ImpactOS fork on own DB `iudbrdewwwxcgoomccfz`; life-science exercises MedDevice/Biotech tracks; LSNS populator already maps their data). Alternate: Ignite/BioPort (never migrated to BAI). Pending Matt's call.
5. **Capture model: three layers.** (a) Sources — interactions (email/meeting/text between parties), submissions (founder-reported), artefacts (deck/spreadsheet/BAI template); raw, dated, immutable. (b) Facts — typed tables at natural grain with `as_of` + provenance (source id, confidence, claim type fact/inference/assumption): funding_events, milestone_reached, team_changes, metric_observations, contact/company profile changes, program_memberships. Both channels feed the same fact tables. (c) Reporting views — monthly snapshot per company and BAI quarterly roll-ups derived, not stored. Grain answer: facts free-dated, reporting periodic. Matt: "good starting point, room to improve."
6. **"How things are done" = Markdown in the repo, versioned in git, referenced by skills** (treated as agentic code). Dividing rule: if a report joins on it → table (programs, cohorts, coach assignments, company↔track, org identity); if an agent needs it to decide behaviour → Markdown (intake process, update definition, cadence, who to ask, review policy). Skills reference files, don't embed. Mirror `.claude/skills` ↔ `.agents/skills`. Interview agent's first job on onboarding is to WRITE these files.
7. **Agent access: CLI primary, MCP secondary.** MCP is a thin wrapper over the same command layer as the CLI (one code path for preview/confirm, allowlists, idempotency). CLI uses per-user token (never service key), `--json` on every command, and is the single door used by hosted forms / email ingest too.
8. **Supabase-first, migrations plain SQL.** Quarantine Supabase specifics: RLS policies call one helper wrapping `auth.uid()`; storage buckets / pg_cron / vault in their own named migrations. Numbered migration files are the record; no declarative-schema workflow; live DB never source of truth.
9. **Meetings: tables + vendor-neutral intake, no capture.** Assume Fireflies / Granola / Fathom / etc. Tables: meetings, participants, transcripts; meeting is an interaction type. Dedup on (source, source_meeting_id). Email→person→company resolution; no supported-company participant → store, don't fire downstream. Two intake paths, one normalised contract: API pull adapter (Fireflies) + CLI file ingest (Granola/Fathom exports). Extraction to claims via observer contract, vendor-agnostic.
10. **Interfaces v1: BAI template export (concrete) + A2UI blueprints rendered locally (ephemeral); hosted dashboards deferred.** A2UI (a2ui.org) is a protocol: agent emits JSON blueprint, host renders with org's catalog; Matt's POC at `/Users/matt/Development/A2UI` (ShadCN catalog: Card, Button, Input, Select, Table, Column, Row, Text; pinned v0.9.1; coach "after meeting" harness against ImpactOS). Harnesses don't render A2UI natively → ship a minimal local renderer; every view-producing skill emits blueprint + Markdown fallback. Keep catalog tiny, pin version.
11. **Onboarding interview: program lead, one question at a time.** Outputs: operating notes (Markdown), seeded reference data (programs, cohorts, coaches, default track), source map (which files/tools hold which schema parts). Resumable: every answer written immediately; interview state is a repo file; resumes across harnesses. Read-before-ask: if an artefact holds the answer, read and confirm. Ends by proposing the first ingest.
12. **v1 parsers: three.** BAI template (lift `parse_template.py` / `verify_payload.py` from baimetrics), generic spreadsheet/CSV with agent-proposed column mapping the user confirms (reuse partner-prep rule: never infer demographics/company type/funding), meeting transcripts (decision 9). Decks/PDFs/email stored as evidence, extracted to claims, no structured parser.
13. **CLI deterministic; judgment in the harness via skills.** CLI ships with one secret (DB token); no model keys or provider choice. Consequences: provenance records harness-reported model + skill version (audit trail, not guarantee); harness-less paths (hosted form, email) are deterministic only — free text is stored raw and queued for the next staff session's extraction skill, queue visible in CLI; skills versioned like code, claims record skill version.
14. **Distribution: GitHub template repo named "impactOS Agent" under the `Volta-Labs-Inc` GitHub org (not MattVOLTA).** Contents: migrations (plain SQL), CLI, skills in `.claude/skills` + `.agents/skills`, A2UI local renderer, blank operating-notes folder, interview state file. "Use this template" → one setup command (provision Supabase, apply migrations) → onboarding interview. README must state it is a separate single-org starter, not a version of Volta's impactOS / Coach OS / Multi Tenant.
15. **Anchor = a versioned "direct beneficiary reporting profile", not the BAI spreadsheet.** Matt: the spreadsheet is one government-approved configuration of the direct-beneficiary reporting requirement; orgs should be able to extend. Public sources for the indicator set:
   - ISED BAI Performance Measurement Framework company questionnaire (annual, per supported company): legal name, CRA BN, year incorporated, year of first sale, 6-stage scale (Idea/Discovery/Validation/Efficiency/Scale/Mature), 14 verticals, founder counts by demographic (women, ≤39, Indigenous, first-time, racialized [opt], LGBTQ2+ [opt]), FT (30h+)/PT employees in Canada + outside Canada, annual revenue, export revenue, financing by source (bank credit, personal, friends/family, gov loans/grants, angel, VC, crowd, other), patents applied/granted, NPS, impact rating. Client definition: sustained interventions over months, not events/walk-ins. https://ised-isde.canada.ca/site/sme-research-statistics/en/business-accelerators-and-incubators/bai-performance-measurement-framework/business-accelerator-and-incubator-performance-measurement-survey
   - RDA performance grid (CED 2024–2028 incubator/accelerator guide): businesses assisted, avg coaching/mentoring hours per business, jobs created and maintained, total sales, total + avg funding received, survival rate. https://www.canada.ca/en/economic-development-quebec-regions/financing-services/support-for-quebecs-business-incubators-and-accelerators-call-for-proposals/ced-support-for-incubators-and-accelerators-2024-2028-application-guide.html
   - PacifiCan glossary definitions: jobs created/maintained = FTE, "maintained" = would be lost without project; "diverse groups" = persons with disabilities, Indigenous, youth, immigrants, racialized, 2SLGBTQ+, women, OLMC (matches BAI's 9 flags). https://www.canada.ca/en/pacific-economic-development/services/funding/funding-program-glossary.html
   - BAI template v5 = ACOA-approved configuration + direct-vs-industry-partner split (baimetrics epic #247). ACOA "direct beneficiary" clause text is in Volta's contribution agreement — restricted (VI card `acoa-funding-and-reporting`), not public. ACOA 2020 innovation evaluation notes gaps in client-level data and recommends the national PMF.
   Design: profile is a contract file (like template-contract-v5.json) = union of ISED PMF + RDA grid + ACOA clause; BAI template is one export mapping; orgs extend. Vindicates per-person demographics (ISED founder counts) and per-engagement support time (coaching hours per business). Adds vs BAI: year of first sale, export revenue, employees outside Canada, financing sources incl. personal/friends/crowd, patents, NPS, survival. Yet another stage taxonomy (ISED 6) → map from tracks.
   **v1 done bar:** every field in the reporting profile populatable from DB for the first adopter's real data, with an explicit list of unfillable fields and why. Populator diff is a check inside that, not the goal.
